# 题目 02 需求说明：宠物门店预约闭环

状态：需求分析草案，待学生审核。来源为教师题集的题目 02 及其共同要求；项目决策以根目录 `AGENTS.md` 的 D01–D14 为准。本文件不是实现通过或验收通过的证据。

## 1. 目标与边界

一家门店发布洗护时段，宠物主人为自己的宠物预约并支付全款；前台核销到店，服务人员登记服务，客服处理临近或开始后未核销的取消申请及退款失败，店长核查当日预约和资金去向。所有业务分支须可操作、持久化，重启后可查，失败原因可见。

教学数据：一家门店、一个项目、三个未来时段，每时段容量 3 只，单次价格 9900 分；用户和宠物预置。模拟支付渠道须支持成功、失败、超时和重复通知。无需真实支付、会员、优惠、多店结算、排班优化或争议退款裁决。

## 2. 角色与权限

| 角色 | 发起/处理 | 查询范围 | 禁止行为 |
|---|---|---|---|
| 店长 | 发布时段，时段结束后标记未到店并填写原因 | 本店时段、预约、日清 | 在时段结束前标记未到店 |
| 宠物主人 | 预约自己的宠物、付款、取消或申请取消 | 本人预约、服务及退款结果 | 操作他人的宠物或订单 |
| 前台 | 核销本店已确认且无待审取消的预约 | 本店待接待记录 | 跨店、重复、取消中或未付款核销 |
| 服务人员 | 对已核销预约登记开始、完成 | 本店服务任务 | 跳过核销、重复完成 |
| 客服 | 批准/拒绝临近取消、跟进失败退款 | 待审与待处理退款 | 把退款失败的预约恢复可用 |
| 模拟支付渠道 | 返回支付/退款结果 | 仅回调关联交易 | 未鉴权回调或用同一事件重复生效 |

正式系统为各预置账号提供账号密码登录，密码仅保存加盐慢散列；登录成功后由服务端维护会话，按会话账号查询角色、门店与宠物归属并逐请求鉴权。登出和过期会话不再授权。请求中的角色或任意用户编号不得成为授权依据；原型中的角色切换仅用于展示页面状态，不是登录实现（D14）。会话 Cookie 应启用 `HttpOnly`、`Secure`、`SameSite`，状态变更请求另需防跨站请求伪造校验；明文 HTTP 的正式目标地址须在启用登录前解决 HTTPS/TLS 入口。

## 3. 业务记录与状态

建议分别保存 `slot`、`booking`、`payment`、`cancellation_request`、`refund`、`service_event`、`exception`、`audit_log`。这是一份逻辑记录清单，不预设最终表结构；D10 已决定分表保存预约、支付、退款、履约与异常/审计。金额以整数分存储，展示为元（D01）。时段输入和展示采用 `Asia/Shanghai`；2 小时规则用实际时刻比较；“当日”指该时区的自然日 `[00:00, 次日 00:00)`（D13）。

预约主状态及合法转换：

```text
PENDING_PAYMENT ──支付成功──> CONFIRMED ──核销──> CHECKED_IN
       │                          │                   │
       ├─5分钟超时──> CLOSED      ├─提前取消──> CANCELLED  └─开始──> IN_SERVICE ──完成──> COMPLETED
       └─主动取消──> CANCELLED   ├─临近取消──> CANCEL_REVIEW ─批准──> CANCELLED
                                  │                   └─拒绝──> CONFIRMED
                                  └─时段结束未到店──> NO_SHOW
```

上图只表示主状态；支付、退款及取消审核必须有独立状态/事件。取消获准时预约即不可核销，即使退款仍在处理或失败。`CLOSED` 后到达的支付成功只记异常并发起退还，不恢复预约。`CHECKED_IN`、`IN_SERVICE`、`COMPLETED` 不走本题取消退款流程。

已确认且未核销的预约在时段开始后仍可提交带原因的取消申请；若时段已结束但尚未标记 `NO_SHOW`，仍按该状态条件申请。申请与未到店标记只有先成功改变状态的一方生效；已标记 `NO_SHOW` 不再进入本题取消退款流程（D12）。

## 4. 业务规则与验收映射

| 编号 | 必须成立的规则 | 可操作验证 | 对应决策 |
|---|---|---|---|
| R01 | 店长按业务时区创建起止明确、未开始的时段；已开始时段不可新预约 | 创建时段、推进教学时钟至开始后尝试预约 | D07、D13 |
| R02 | 同宠物同一时段只有一个有效预约，单时段有效占位至多 3 | 重复预约与多人抢最后名额 | D02、D05 |
| R03 | 待付款占位 5 分钟；超时/主动取消只释放一次 | 推进 5 分钟、重复超时/取消，再让新用户预约 | D02、D07 |
| R04 | 有效支付确认一次；失败不确认；关闭后迟到成功记异常并退款 | 成功、失败、重复、超时及迟到回调 | D09、D10 |
| R05 | 距开始至少 2 小时的已确认预约可直接取消并全额退款；按实际时刻计算差值 | 恰好 2 小时及其前后边界，跨本机时区复测 | D03、D07、D13 |
| R06 | 开始前不足 2 小时，或开始后仍已确认且未核销、未标未到店的取消须说明原因并由客服审批；待审仍占位、不能核销；批准后全额待退 9900 分 | 开始前后及结束后未标未到店申请、批准/拒绝、待审核销及退款金额 | D05、D11、D12 |
| R07 | 取消获准后不能核销；退款失败可跟进/重试，预约不复活 | 退款失败、重试、重复退款结果 | D09–D11 |
| R08 | 仅本店前台核销已确认且无待审取消的预约；服务只能按核销→开始→完成 | 非本店、非法状态、重复核销/完成 | D04、D06 |
| R09 | 核销与取消竞争仅有一个合法结果，名额和金额不重复变动 | 可重复并发测试，另一操作得到冲突 | D05 |
| R10 | 时段结束后未到店由店长写原因，用户可见且不自动退款；待审取消不可同时标未到店 | 申请与未到店标记竞争、查看结果和日清 | D06、D07、D12 |
| R11 | 按 `Asia/Shanghai` 自然日，日清分列有效预约、完成、取消、未到店、退款待处理及已收/已退/未退金额 | 跨 UTC 日期的同一天四类记录，逐笔对账 | D01、D10、D11、D13 |
| R12 | 账号密码登录与服务端会话限定角色及数据归属；业务结果和失败原因可操作且持久化 | 错误密码、未登录/登出/过期会话、伪造角色或用户编号、跨用户/店操作、重启后查询 | D08、D09、D14 |

“有效占位”至少包括未超时待付款、已确认、待取消审核和已到店/服务中的该时段预约；取消或关闭可释放名额一次。已完成服务不应被误当作可重新销售的同一时段名额。名额计算及状态变化应在数据库事务/条件更新中保持一致，不以页面计数代替。

金额核查从交易记录推导：`已收款=支付成功总额`，`已退款=退款成功总额`，`未退款=已收款-已退款`；已完成服务金额单独按履约结果统计。关闭后迟到支付与其退款也必须能逐笔解释，不应把所有已付款当作已完成服务。

## 5. 五组必须演示的闭环

| 场景 | 起点 → 终点 | 关键证据 |
|---|---|---|
| S01 正常接待 | 发布→预约→支付→核销→开始→完成→双方查询 | 预约/支付/履约事件及页面结果 |
| S02 名额循环 | 并发争抢→仅合法数量成功→未付款超时或取消→新预约 | 数据库占位数、冲突/超时结果 |
| S03 取消分支 | 提前自动取消；临近分别批准/拒绝；退款失败重试 | 审核原因、退款状态及用户结果 |
| S04 现场冲突 | 取消与核销并发；重复核销；非本店核销 | 唯一终态、拒绝原因、无重复金额 |
| S05 收店核查 | 已服务、取消退款、未到店、退款失败同日共存 | 店长逐时段与逐笔金额核查 |

### 原型页面状态说明

`prototype/index.html` 是无后端、无持久化的可点击原型。角色切换、员工归属和支付结果都只模拟页面状态；不会在原型里伪造账号密码登录或服务端会话，不能作为正式权限或真实支付的实现证据。

| 页面 | 主要操作 | 结果与异常状态 |
|---|---|---|
| 宠物主人 | 切换预置用户、预约、模拟支付、取消/申请 | 待付款、已确认、取消待审、已取消、超时关闭、服务结果；重复预约、名额不足、渠道失败/超时及迟到支付 |
| 前台 | 以本店/非本店员工模拟核销 | 窗口外、未确认、待审取消、重复与跨店核销的失败原因 |
| 服务人员 | 开始、完成服务 | 未核销或重复操作失败；已开始可在时段结束后补完成 |
| 客服 | 批准/拒绝临近或开始后未核销的取消、模拟退款失败和重试 | 待审、拒绝、退款待处理/失败/成功；获批后显示全额待退 9900 分 |
| 店长 | 按 `Asia/Shanghai` 发布时段、按该时区日期预览日清、标记未到店 | 占位、完成、取消、未到店、退款待处理与金额；页面仍仅为内存预览 |

教学时钟按钮只推进页面内存，不等于 D07 所要求的数据库持久化教学时钟。原型不能真实模拟并发，只展示状态冲突的反馈；并发结果须在正式系统和测试中验证。
