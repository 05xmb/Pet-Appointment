# 宠物预约题目验收检查

## 用途

依据题目 02 原文逐项验收宠物门店预约系统，覆盖角色权限、完整业务闭环、异常路径、持久化、测试证据和部署结果。验收 Agent 不根据开发 Agent 的“已完成”声明直接判定通过。

## 触发场景

- 开发 Agent 提交可验收版本。
- 测试和修复完成后准备发起 PR 或部署。
- 主分支合并后需要确认实际发布版本。
- 需要复核题面中的正常、异常、权限和日终核查场景。

## 输入

1. 原始题目 02 文本。
2. 项目 `AGENTS.md` 和已确认的学生决策表。
3. 待验收提交哈希、运行地址、数据库初始化数据和模拟支付服务。
4. 测试命令、覆盖率原始输出、缺陷复测记录和流水线记录。

## 执行步骤

1. 确认验收版本、部署版本和测试版本的提交关系；不一致则标记阻塞。
2. 核对角色：店长、宠物主人、前台/服务人员、客服和模拟支付渠道的权限边界。
3. 验证正常流程：发布时段 → 预约付款 → 核销 → 服务开始 → 完成 → 用户和店长查询。
4. 验证名额循环：并发抢位、未付款 5 分钟超时/主动取消、名额恢复和再次预约。
5. 验证取消分支：提前至少 2 小时、临近开始审核、批准、拒绝、退款失败和重试。
6. 验证现场冲突：取消与核销并发、重复核销、重复完成、非本店前台操作。
7. 验证支付异常：重复成功通知、关闭后迟到支付、异常登记和退款，不得恢复已关闭预约。
8. 验证时段结束后的未到店标记、原因记录和用户可见结果。
9. 核对日终结果：有效预约、已完成、已取消、未到店、退款待处理、已收款、已退款和未退款金额。
10. 检查数据库重启后的业务结果、页面失败原因、测试覆盖率、`go vet`、竞争检测和部署健康检查。

## 输出格式

```markdown
# 题目 02 验收报告
- 验收提交：
- 部署版本：
- 验收时间：
- 总结：通过 / 不通过 / 阻塞

## 逐项结果
| 编号 | 原题要求 | 操作或命令 | 结果 | 证据 |
|---|---|---|---|---|

## 缺陷与阻塞
| 编号 | 严重度 | 复现步骤 | 预期 | 实际 | 状态 |
|---|---|---|---|---|---|

## 未覆盖项

## 复验结论
```

每个“通过”必须有操作结果、日志、页面、数据库查询或测试输出中的至少一种证据；没有证据只能写“未验证”。

## 失败处理

- 题面、决策表、代码版本或部署版本缺失：暂停并报告阻塞。
- 发现缺陷：记录原始结果，不删除失败测试、不降低断言、不修改验收标准。
- 开发 Agent 修复后，只复验受影响项并重新执行必要的回归项。
- 主分支合并或部署提交变化后，不能沿用旧版本的通过结论。

## 完成标准

- 正常流程和题面要求的全部异常场景都有逐项结论。
- 权限、名额、支付、退款和履约数据一致。
- 服务重启后仍可查询业务结果。
- 测试、覆盖率、质量检查、部署和冒烟检查证据齐全。
- 所有未决事项明确标为阻塞或由学生决策，不被隐式放行。
